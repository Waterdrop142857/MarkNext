# 测试流程与质量检查

按任务选择验证流程。用户报错先在独立会话中运行完整 Tauri 程序复现，确认故障后才开始定位和修复。常规开发按影响范围选择相关测试，纯文档修改检查内容和差异。`pnpm check` 保留为按需执行的完整检查入口，其流程不包含真实桌面交互验收。

## 用户报错反馈处理流程

本流程适用于报错文字、崩溃、卡顿、布局异常及操作无效等反馈。每次新的失败反馈都重新确认实际故障，既往测试通过记录不能替代本次复现。除用户明确调整顺序外，依次完成以下阶段。

### 1. 记录反馈与基线

- 记录报错原文、截图、最短操作步骤、预期结果和实际结果。整理系统、应用版本/提交及已有工作区修改、启动方式、桌面与显示后端、语言、主题、缩放、编辑模式和相关设置，只补充当前故障需要的信息。
- 区分 `pnpm tauri dev`、生产二进制和实际安装包，区分冷启动、已有窗口及恢复会话。记录相关文件的扩展名、编码、路径特征、大小及未保存状态。
- 首先检查 Git 状态及启动配置，固定本次基线，保护已有未提交修改。准备合成文件或经用户允许的副本，保留触发问题的路径和内容特征。用户数据不能直接作为可能被覆盖、移动或删除的测试文件。

### 2. 建立独立原生会话

- 为本次反馈创建专用图形会话、应用进程、配置/缓存/恢复目录和临时测试文件。Linux 使用私有 D-Bus 会话，防止单实例请求送进用户正在使用的窗口。Windows/macOS 使用独立测试账户或虚拟机。已有用户设置是触发条件时，只将必要设置复制到测试会话，并记录差异。
- Linux X11 可使用空闲显示编号的 Xvfb，Wayland 问题使用独立的原生或嵌套 Wayland 会话。运行后确认 Tauri 和外部程序实际使用的显示后端。嵌套 Weston 可用于排查通用 Wayland 路径，仅在 niri 等特定合成器发生的问题仍需匹配该合成器。软件渲染或虚拟显示可能改变渲染/性能表现，无法重现时应核对这些差异。
- 从真实应用入口运行 Tauri，加载实际 Vue 应用、编辑器、Rust 后端及平台 WebView。开发模式启动完整 `pnpm tauri dev`，生产问题使用当前基线构建的生产二进制。安装、文件关联和图标问题使用相应安装包及系统入口。
- 拖放从实际外部程序发起，系统剪贴板、文件对话框、磁盘变化和窗口关闭通过相应系统交互触发。可用外部原生测试源缩小复现条件，反馈指向特定文件管理器时仍需用该程序复现。Playwright 测试入口、模拟 IPC 或脚本派发的 DOM 事件属于补充验证。
- 确认新进程确实创建了本次测试窗口，记录进程、命令、显示后端及服务端口。端口被占用时先确认归属，不复用来源不明的开发服务器，也不终止用户进程。结束后只清理本次拥有的进程和会话，保留诊断产物。

Linux 已准备好专用图形会话后，可以在其终端中初始化数据隔离。以下命令继承当前 `DISPLAY` 或 `WAYLAND_DISPLAY`，执行前必须确认它们属于测试会话。

```bash
mkdir -p test-results
MARKNEXT_TEST_ROOT="$(mktemp -d "$PWD/test-results/native-feedback.XXXXXX")"
mkdir -p "$MARKNEXT_TEST_ROOT"/{config,data,cache,files}
export MARKNEXT_TEST_ROOT
dbus-run-session -- env \
  XDG_CONFIG_HOME="$MARKNEXT_TEST_ROOT/config" \
  XDG_DATA_HOME="$MARKNEXT_TEST_ROOT/data" \
  XDG_CACHE_HOME="$MARKNEXT_TEST_ROOT/cache" \
  bash --noprofile --norc
```

后续应用及外部测试程序均从上述私有 shell 启动，继承同一组会话变量。在项目根目录运行开发版并保留标准输出和错误输出。

```bash
pnpm tauri dev > "$MARKNEXT_TEST_ROOT/app.log" 2>&1
```

该命令前台运行，退出后记录其退出码。需要并行运行文件管理器等程序时，先在同一私有 shell 启动相应程序并记录进程。专用显示会话的建立按本机已有工具完成，不能只建立私有 D-Bus 后继续在用户桌面进行自动化输入。

### 3. 修复前实际复现

1. 在未修改产品代码的基线上重放用户步骤，先确认故障确实出现。复现前限于环境准备、操作记录和现有日志/截图采集，不先根据猜测修改逻辑、加产品诊断代码或改变运行参数来绕过故障。编译或启动故障阻止窗口出现时，在独立会话执行原始构建/启动命令，保留实际失败证据，修复后继续完成完整程序交互验收。
2. 保存可观察的失败证据，包括触发前状态、操作、错误窗口或异常画面、现有日志、退出码及实际文件/编辑器结果。终端无输出时记录这一事实，并检查可获取的进程退出状态及系统崩溃报告。截图可以证明显示异常，正文、保存和历史问题还需比较对应内容与状态。
3. 偶发故障记录尝试次数、发生次数、等待时间和触发顺序，保留至少一次真实失败。冷启动、首次操作与后续操作分别记录，不能用热启动成功覆盖冷启动失败。
4. 未复现时核对构建、后端、设置和输入差异，每次只改变必要条件。缺少信息时询问最小缺口，缺少对应平台或会话时记录具体阻塞。此时状态为“尚未复现”，继续准备复现，不进入原因定位及修复阶段。

### 4. 定位原因与建立回归

- 原生复现成立后，再沿真实入口、平台事件、IPC、文档状态和编辑器路径定位，可添加必要的临时诊断。区分观察事实和待验证假设，记录证据如何解释实际失败。
- 先形成可重放的原生步骤，再在最接近根因的层次补充回归断言，验证这些断言在修复前失败、修复后通过。现有用例已准确捕获故障时直接复用，避免重复测试。
- 原生事件和系统配置问题保留原生验证。涉及 Tauri 运行时配置时检查实际生成的上下文或构建产物，单独读取源配置文件的单元测试不能证明运行时数据相同。
- 确认根因后修改最小范围，沿用共用入口和既有状态约束，避免同时调整无关 UI、依赖或配置。定位用的临时诊断在交付前移除，或明确其保留用途和启用条件。

### 5. 修复后回归与验收

1. 使用修复后的代码重新构建受影响的原生产物。开发模式涉及 Rust、Tauri 配置或插件时重启实际进程，生产模式使用重新打包的资源。保留原始文件和设置基线，为前后比较创建等价的测试状态。
2. 在相同会话条件、启动方式和入口下完整重放原失败步骤，比较修复前后的错误、内容、窗口状态和必要耗时。原生故障必须在原生程序内确认消失，仅编译成功或浏览器测试通过不能结束验收。
3. 按改动选择相关单元、浏览器及 Rust 回归，并在原生程序内检查受影响的相邻场景。涉及文件/历史时检查未保存内容、源文件及撤销重做，涉及异步流程时选择取消、失败、重复操作和过期结果中的相关边界。
4. 前后构建使用可追踪的提交和工作区差异，产物分目录保存。偶发故障按相同条件重复触发并报告次数及结果。性能问题记录相同机器、输入、启动/预热条件和前后测量。
5. 交付报告列出原生复现证据、根因、变更范围、原生重放结果、实际运行的相关测试及未覆盖范围。报告“尚未复现”“已复现”“修复后原生回归通过”“待用户验收”等实际阶段，原生回归未完成时如实说明。

### 复现与验收记录

每次反馈使用独立的 `test-results/native-feedback.<标识>/` 目录，至少保存以下记录。目录已被 Git 忽略，可长期复用的步骤、脚本和合成夹具纳入正式文档或测试，不将用户文件和诊断产物提交仓库。

- `summary.md` 记录反馈、环境、基线、启动命令、步骤、预期/实际结果、复现次数、当前阶段、修复前后证据路径和未验证范围。
- `before/` 与 `after/` 分别保留应用及相关外部程序日志、必要的退出状态、截图或录屏，以及文件/编辑器结果对比。
- `files/` 保留合成输入，并记录必要的设置副本与原生程序构建身份。日志避免输出用户正文或凭据，共享截图和崩溃报告前移除无关私人信息。

已有 Linux 原生拖放脚本及运行方法见下文“Linux 原生文件拖放回归”。它只覆盖声明的 X11 拖放场景，其他反馈仍需为对应场景建立原生复现和验收步骤。

## 按影响范围选择测试

用户报错均须完成上述原生复现及修复后重放。下表用于选择额外回归，也用于普通开发任务的验证选择，不要求每次执行全部测试。

| 变更范围 | 相关验证 |
| --- | --- |
| 文档或流程说明 | 阅读内容、链接、命令与当前实现的一致性，检查差异 |
| 纯函数、文档用例和状态 | 对应 Vitest，涉及 TypeScript/Vue 时运行类型检查 |
| 编辑器、布局、输入和设置 | 对应组件/浏览器测试，检查相关模式、主题、语言或缩放 |
| Rust、文件 I/O、原生队列和窗口接线 | 对应 Rust 测试、格式与编译检查，在真实应用入口验证受影响行为 |
| 拖放、剪贴板、焦点和系统对话框 | 原生程序与真实系统交互，按问题选择相关浏览器/单元回归 |
| 启动、卡顿和大文件性能 | 对应启动方式的原生测量，区分冷启动和预热，记录相同输入的前后结果 |
| 安装器、文件关联和图标 | 对应平台安装包、系统入口和相关配置/资源检查 |

浏览器项目按当前任务适用的用户指令选择。Playwright WebKit 与 Linux Tauri 使用的系统 WebKitGTK 分别记录，跳过前者不取消原生复现和验收。环境无法满足时记录阻塞，不能删除断言、扩大超时或反复重试直到成功。只有共享契约影响扩大、相关失败暴露更广风险或用户要求时，才扩大测试范围。已通过且没有后续相关变更的检查不重复执行。

## 自动化检查约定

任何检查失败立即返回非零退出码，后续阶段不继续执行；不自动重试失败测试，Vitest 和浏览器测试不允许 `.only`，Vitest 的未处理异常会令流程失败。浏览器测试还会检查未捕获异常、console.error 与意外的外部网络请求。

## 环境准备

需要 Node.js 24+、项目固定的 pnpm 11.28.3、Rust stable（含 rustfmt/clippy）以及当前平台的 Tauri 系统依赖。仅按选定的测试范围准备环境，已有环境可用时直接复用。使用锁文件安装前端依赖，并按需准备浏览器项目。

```bash
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
```

需要 Playwright WebKit 时再执行 `pnpm exec playwright install webkit`。在受支持的 Linux 系统（例如 Ubuntu 24.04）可以为选定项目同时安装浏览器及系统依赖。

```bash
pnpm exec playwright install --with-deps chromium
```

新增 jsdom 27.4.0、@playwright/test 1.58.2 前，已核对 npm 官方 registry 的名称、版本、repository、tarball/integrity，以及官方源码 package.json 的名称与版本。固定精确版本并记录锁文件，后续增加/升级依赖也应先确认真实存在、来源可信。

原生会话工具按故障场景准备。下载额外工具或兼容库前核对准确名称、官方来源和元数据，只在测试目录使用必要的兼容环境，不为测试替换用户系统库。浏览器依赖准备不能替代 Tauri 系统依赖检查。

## 命令

| 命令 | 范围 |
| --- | --- |
| `pnpm check` | 类型检查、全部前端测试、Rust 检查、Tauri 发布二进制、Chromium/WebKit 回归 |
| `pnpm check:frontend` | 类型检查、全部前端测试、生产前端构建、两个浏览器回归 |
| `pnpm check:native` | Rust fmt/check/test/clippy、实际 Tauri 发布二进制构建、plain release check/clippy |
| `pnpm test` | 全部 Vitest 测试（包括文档动作） |
| `pnpm test:e2e` | 先构建生产前端，再运行全部浏览器回归 |
| `pnpm test:unit` | 所有 `src/**/*.spec.ts` 与文档动作测试，不含历史审计复现 |
| `pnpm test:document-actions` | Vitest 的文档动作与窗口关闭测试 |

单文件回归使用 `pnpm exec vitest run <相关文件>`。浏览器回归先执行 `pnpm build` 更新当前生产资源，再运行 `pnpm exec playwright test --project=chromium <相关文件>`，需要时选择 `--project=webkit`。Rust 回归使用 `cargo test --locked --manifest-path src-tauri/Cargo.toml <相关过滤器>`。明确记录未覆盖的范围，需要全量检查时再选择上表的完整入口。

`scripts/check.mjs` 负责跨平台串行执行和退出码传播，支持 pnpm JS 启动器与 Unix/standalone 启动器。Rust 命令使用 `--locked`；Tauri CLI 也将该参数传给 Cargo，实际验证 beforeBuildCommand、production 资源、release feature flags 和链接。流程使用 `--no-bundle`，验证可执行文件，不依赖签名、商店账户或安装器打包环境。

## 测试层次与 P1 回归

多文件与单窗口新增覆盖：`src/composables/__tests__/documentTabs.spec.ts` / `nativeFileRequests.spec.ts`、浏览器 `documentTabs.spec.ts` / `nativeFiles.spec.ts` 及 Rust `window_instance` 测试。覆盖每文件历史/模式隔离、唯一活动渲染器、关闭事务、路径去重、恢复、原生请求队列及安装器配置。浏览器原生 IPC 仍使用官方 mocks，窗口管理器焦点和安装后的文件关联按 [手动指南](../docs/multi-file.md#手动验收) 在对应系统验证。

冷启动覆盖：`src/services/__tests__/startup.spec.ts`、`src/editor/__tests__/loadEditorSession.spec.ts`、浏览器 `startup.spec.ts` 及 Rust `window_instance::tests` 验证前置主题、开发/生产入口延迟、显示后的空闲预加载与按需加载共享、失败后的重新加载、窗口就绪代号及带值启动参数。流程和人工验收见 [启动设计](../docs/startup.md)。

- Vitest 保留原测试声明的 happy-dom/jsdom 环境。安全净化用例使用 jsdom；happy-dom 对此版本 DOMPurify 的支持不完整，不以它证明净化安全。CSS inline 导入启用真实 KaTeX、Prism、GitHub Markdown 和 exportStyle 内容，避免空字符串产生误通过。
- `documentOpen.spec.ts` 使用真实 Muya、真实 workspace/actions，并控制 RAF 与 IPC 完成时序。覆盖读取期间排队编辑后的保存/丢弃/取消、已批准版本不重复询问、确认期间的新编辑、读取失败和 generation 变化；读取只执行一次。另覆盖新建、关闭窗口和退出时，确认期间新输入的内容不会被此前的丢弃选择覆盖。
- `htmlPreviewIsolation.spec.ts` 使用真实 Muya，验证大小写样式表、危险行内布局、SVG 动画/事件属性、允许的普通样式，以及源 Markdown 不被净化改写。行内 HTML 与块预览使用同一 CSS 策略。
- Vitest 文档动作测试覆盖新建、打开、关闭、退出与系统关闭的统一保存保护、保存失败、重复操作和监听器生命周期。
- 浏览器回归挂载真实 Vue 应用与编辑器，通过 Tauri SDK 的官方 mocks 控制磁盘和对话框 IPC；Chromium/WebKit 分别验证延迟读取期间的实际输入、三种确认选择、CSS 净化与真实布局/菜单点击，以及生产 dist 隐藏开发者工具、正常启动。页面只能访问本地测试服务器，外部请求会被阻止并令测试失败。
- `/tests/e2e/fixtures/host-style.css` 是真实存在的测试样式表。浏览器测试会确认原始 HTML 的 link 被移除，且没有请求该文件；不会下载外部“恶意 CSS”。
- `mermaidTheme.spec.ts` 使用真实 Mermaid，覆盖流程图、时序图、类图、状态图和 ER 图。验证暗色连接线及箭头在编辑器与浮层背景上达到 3:1 对比度，时序消息文字达到 4.5:1；亮色、暗色与跟随系统之间切换保留原 SVG/编辑器实例，恢复浅色配色，保留显式 linkStyle 线条颜色和空心标记语义。
- P2 的 SourceEditor/search 单元测试覆盖空查询、无关选区、内容变更后的偏移、大小写与整词选项、替换后下一匹配、模式切换保留历史以及新文档/外部内容使旧历史失效。
- `diagramRevision.spec.ts` 用受控 renderer 加载和延迟绘制验证旧成功/失败、清空、销毁、移除、重复请求以及 Vega view.finalize 清理。每个版本在独立目标渲染，断言晚到回调无法改写最新预览。
- `documentImages.spec.ts` 覆盖 POSIX/Windows/UNC、上级目录、中文、空格及编码路径，另存为后的目录更新，权限请求合并、先授权后加载和失败重试。Rust 单元测试验证只接受存在的图片文件，并拒绝非图片、目录、缺失文件和伪装扩展名的符号链接。
- `p2.spec.ts` 在两种浏览器里验证真实应用的搜索、源码历史与文件/模式边界，行内/引用/HTML 图片目录更新，以及 640×480、800×500、1024×720 下两种编辑模式的内部滚动。图片的原生 convertFileSrc 在测试入口映射到本地 SVG fixture，磁盘授权由 IPC mock 记录；这不是原生 asset 协议的端到端测试。
- `textDrag.spec.ts` 用真实鼠标拖动文字，验证同段及跨段移动后的正文/源码一致、单步撤销重做、Backspace 与 Ctrl+A 删除，避免浏览器复制出未关联文档节点的“幽灵文字”。`dragDropText.spec.ts` 另覆盖两种落点光标 API、反向选区、复制修饰键、落在原选区内、外部纯文本、过期拖动、输入法/只读保护、图片兼容及监听清理。文字拖放通过文档状态提交；落点无法解析时取消，浏览器的原生拖放插入与删除不直接修改编辑器 DOM。

`tests/e2e/app.html` 是 Vite 开发服务器下的测试入口，先准备 mock 再导入真实 src/main。生产构建只从 index.html 进入，不包含该入口及原生 mocks。另一个测试服务器用 vite preview 提供真实生产 dist。二者端口固定为 4173/4174，严格禁止端口自动切换和复用已有服务，避免测试误连其他实例。

## Arch Linux 的 Playwright WebKit

本机 ICU 78 与下载的 Ubuntu WebKit 所需 ICU 74 有不同的动态库名和版本符号；不要用软链接伪装版本。Playwright 的受支持 Ubuntu 环境可由 `install --with-deps` 准备；Arch 可选择受支持容器，或独立兼容运行目录。

本次本地验证从 Ubuntu 官方仓库取得 libicu74 74.2-1ubuntu3.1、libflite1 2.2-6build3，只解包到 `/tmp/marknext-playwright-libs`，没有安装或替换系统库。由于 Playwright 打包启动器会覆盖 LD_LIBRARY_PATH，临时 `/tmp/marknext-webkit-run.sh` 设置对应 WebKit 路径与兼容库后启动原浏览器二进制。

该环境可用于相关 WebKit 浏览器回归，先更新当前生产资源。


MARKNEXT_WEBKIT_EXECUTABLE 只覆盖 WebKit 的启动器路径，测试项目、用例与断言完全相同；缺少运行库依旧失败，不会跳过 WebKit。临时文件可能被系统清理，之后需重新准备兼容环境。Release 工作流不运行浏览器测试。

## 外部修改保护与草稿恢复验收

`documentSafety.spec.ts` 单元测试验证保存时的磁盘版本保护、覆盖确认期间再次修改、检查结果晚到、排队保存版本、恢复副本和备份/清理队列。Rust 测试使用真实文件验证版本冲突、临时文件写入后的再次校验、恢复记录落盘、编码和损坏记录保留。浏览器同名用例验证完整 UI、取消确认、两种文档来源的重启恢复、恢复副本、保存后清理及尚未查看记录的保留；重启由页面重新加载和持久化原生 fixture 模拟。

大文件浏览器用例打开约 1.13 MB、5000 行的文档，再切换到源码模式，验证可视区渲染的行数小于 200、末尾编辑以及撤销后全文一致。测试输出文件长度、实际渲染行数和打开至切换完成的耗时；磁盘 IPC 使用 fixture，该耗时包含 Muya 初次渲染和测试操作，不代表 Tauri 实机加载时间。单元测试另验证元数据不变时不重复计算全文版本，已确认的外部版本也不重复读取或更新提示。

真实 Tauri 窗口按以下步骤验收：

1. 打开同一 Markdown 文件，用其他编辑器修改，再回到 MarkNext。分别检查有无本地修改的情况，都应先询问保留编辑器内容还是加载磁盘内容；关闭询问应保留内容。保留后反复切换窗口或等待多轮检查，同一外部版本不重复询问；再次外部修改后应重新询问。选择加载后内容更新，编辑模式保持不变；有未保存修改时询问应明确提醒将丢弃这些修改。
2. 在有冲突时直接保存，确认不会覆盖外部内容。测试“重新加载”的取消/不保存、“另存为”，以及“保存我的版本”的取消/确认；覆盖确认期间再外部修改，保存应再次停止。
3. 外部删除文件，再在 MarkNext 保存，确认普通保存不自动重建文件，编辑仍可另存为。
4. 分别编辑已有文件和未命名文档，停止输入至少 1 秒后强制终止应用进程，再启动。通过提示或“文件 → 恢复未保存文档”恢复，检查内容、编码、模式和光标；恢复操作本身不写原文件。
5. 强制退出后先在外部改变或删除原文件，再恢复。确认以未保存副本打开，普通保存进入另存为流程。
6. 保存或选择“不保存”后正常关闭，再启动应不再出现当前草稿；未查看的其他记录仍然可恢复。删除恢复记录必须确认，原文件保持原样。
7. 在应用数据目录的 `recovery-v1` 中放入损坏 JSON，启动后其他正常记录仍可恢复，损坏文件保留并提示。备份失败时显示重试入口；恢复存储后重试应写入最新内容。
8. 使用大 Markdown 文件分别检查所见即所得和源码模式的打开、滚动、末尾编辑、搜索和撤销；静置时后台检查不应每 5 秒读取全文。区分普通长文本与大量公式/图表，后者还有独立的预览渲染成本；源码可视区渲染不代表 Muya 已实现全文虚拟化。

突然终止进程前尚未完成的备份无法保证落盘，持续输入时最多约 5 秒的最近改动可能尚未记录。跨进程写入不受应用内部锁保护；最后版本检查与重命名间的极短竞争窗口仍需注意，不宣称提供跨应用事务锁。


## 历史检查点与渲染器生命周期验收
